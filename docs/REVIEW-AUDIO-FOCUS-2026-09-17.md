# 跨应用音频接管

## 原因和修复

原实现只有全局 `reserved` 布尔锁，新的应用遇到占用就失败；局部播放器的停止、
释放也没有标识所属请求。直接删掉互斥会造成共享 I2S 并发初始化、旧任务关闭新声音，
因此改成“最新请求获胜”的独占音频焦点，而不是多路同时播放。

- `audio_focus.h` 维护非零 lease；旧 lease 不能写入或释放新持有者。
- codec 初始化和每个读写块仍串行，但 HTTP 下载和 ASR 不持有硬件锁。
- 音乐播放使用独立任务及自己的 URL、lease、序号。生成/同步不会再被播放任务占住，
  失效的 HTTP 任务自行退出；同时存活的播放网络任务上限为三个。
- 本地故事、单词和宠物语音的任务独立保存输入，页面只停止属于自己的播放序号。
  宠物 PCM 复制到独立 PSRAM，避免下一次回复修改播放中的内存。
- 被抢占或离开页面的录音丢弃，不上传 ASR、不触发生成。主动提交后的识别仍可后台完成。
- 普通时钟导航不申请焦点，不停止背景音乐；新朗读或录音会接管，不自动恢复被打断的音乐。
- 作品库的播放状态改读真实播放器状态，不再通过字符串中是否有 `PLAYING` 判断占用。

## 回归入口

```sh
cc -Wall -Wextra -Werror -I main tools/test_audio_focus.c -o /tmp/test-audio-focus
/tmp/test-audio-focus
python tools/test_audio_focus_device.py
python tools/test_music_device.py
python tools/device_ui_test.py
```

纯 C 测试覆盖最新持有者、过期释放、取消和零值回绕；隔离副本改成无条件释放时，
测试在旧音乐任务释放新点读持有者处失败。真机测试使用已保存作品，录音全部取消，
不生成新音乐或宠物回复。交叉测试包括：

1. 时钟保留背景音乐；英语点读接管并输出完整音频。
2. 故事接管音乐，音乐再接管故事；旧故事页面隐藏不能误停音乐。
3. 麦克风接管音乐；新播放取消超过一秒的有效长度录音，不能进入上传状态。
4. 音乐播放中可开始音乐创意录音；离开页面取消。
5. 宠物录音接管音乐；离开页面取消，不等待生成回复。
6. 四轮故事与音乐交替接管，无死锁、无旧任务夺回音频。

测试证据保存在忽略的 `artifacts/audio-focus/`，不能提交用户截图和原始串口日志。
公开树检查和固件构建后都必须检查 `dependencies.lock`，防止本机绝对路径被构建器写回。

## 验证边界

同一实现者执行验证，非独立审计。真机播放的证据是实际 codec 驱动写入成功，
不是声学音质评测。未模拟网络接口永久卡死、物理麦克风断线或内存分配失败；
网络线程有超时及并发上限，硬件互斥锁不跨网络操作。没有改变服务器或 Mac Wi-Fi。
只更新设备应用分区，不擦除 NVS、内容、照片、壁纸或已保存作品。
